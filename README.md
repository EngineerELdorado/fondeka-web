# Fondeka Business Web

Next.js App Router + React + strict TypeScript. A separate customer web application for Fondeka’s B2B services, using the existing customer backend and Cognito login.

For other frontend projects adopting this look and feel, share the standalone [Fondeka frontend design and UX guide](docs/fondeka-frontend-design-and-ux-guide.md). It covers progressive forms, polished inputs, page composition, visual tokens and adoption while preserving existing business logic.

## Run locally

Use Node.js 22 LTS (`nvm use`) and npm; Node 20.19+ is also supported. The default port is **4200**, keeping the existing commerce and admin apps separate.

```sh
npm install
npm run dev
```

Open [http://localhost:4200](http://localhost:4200). The default is a clearly labeled demo with fictional data. Demo changes are persisted in this browser only; Settings → Reset demo restores the initial workspace. Demo never falls back to or calls the live backend.

The workspace opens in light mode by default. The sun/moon button in the workspace header and browser verification screen switches between dark and light themes. A saved preference takes precedence over the default, persists in browser storage, synchronizes across tabs, and is applied before first paint. Both themes use locally served Geist typography, layered surfaces, and the Fondeka green accent. Decorative motion respects the system’s reduced-motion preference.

Login uses a compact, plain sign-in card with a clear heading, labeled fields, a solid primary action and the language selector in the card header. A short localized step label identifies email or code entry; resend and change-email actions share a row. The dark desktop brand panel keeps the four-tool preview, with a compact arrangement on shorter screens. Spacing adapts to viewport height so laptop users can see the form and registration action without scrolling. Mobile keeps a compact brand header. Input text remains 16px, and error messages and keyboard navigation remain accessible without clipping the page. The existing email-code authentication and app registration handoff are unchanged.

On phones, the workspace uses bottom navigation, compact lists in place of wide tables, and full-screen forms or bottom sheets. POS keeps the catalog visible with a floating sale total and a cart sheet. Secondary banners are hidden and the integration guide is collapsed; API tools and settings remain accessible from More. Touch controls, input sizes, and safe-area spacing adapt to small screens in both themes.

## Connect the existing backend

Copy `.env.example` to `.env.local`, set `NEXT_PUBLIC_DEMO_MODE=false`, and provide:

```dotenv
FONDEKA_API_BASE_URL=http://localhost:8080
NEXT_PUBLIC_COGNITO_USER_POOL_ID=your-customer-pool
NEXT_PUBLIC_COGNITO_USER_POOL_CLIENT_ID=your-public-customer-client
```

Use a Cognito **customer app client without a client secret**, supporting the existing `CUSTOM_WITHOUT_SRP` email challenge flow. Restart Next.js after changing environment variables; public values are embedded at build time. The customer app client must be accepted by the backend’s JWT audience configuration. Use HTTPS for deployed apps.

The portal reuses the Admin dashboard’s email → OTP authentication pattern, configured for the **mobile app’s customer identity**:

| Portal setting                            | Mobile app setting                  |
| ----------------------------------------- | ----------------------------------- |
| `NEXT_PUBLIC_COGNITO_USER_POOL_ID`        | `EXPO_PUBLIC_USER_POOL_ID`          |
| `NEXT_PUBLIC_COGNITO_USER_POOL_CLIENT_ID` | `EXPO_PUBLIC_COGNITO_APP_CLIENT_ID` |
| `FONDEKA_API_BASE_URL`                    | `EXPO_PUBLIC_API_BASE_URL`          |

The user enters their existing Fondeka email, receives the existing Cognito custom-challenge OTP, and confirms it with `confirmSignIn`. Amplify restores/refreshes the resulting browser session through `fetchAuthSession`; authenticated users visiting `/login` return to their workspace. The same customer account owns their mobile and portal data, while each client maintains its own session. Region is derived by Amplify from the user pool ID. The mobile app’s `fondeka://` OAuth callbacks are not used by this direct email OTP flow. Local sign-out affects this browser session; it does not globally sign the user out of the mobile app.

Registration is available in the mobile app. On `/login`, Register opens the matching App Store/Google Play page on iPhone, iPad and Android; desktop visitors get both store links and locally generated QR codes. Store destinations and device detection match fondeka-website. Login and registration guidance are available in English and French.

The backend URL remains server-only. An allowlisted same-origin `/api/backend/**` gateway forwards the customer access token and trusted-device headers. The backend remains responsible for JWT validation, `CUSTOMER` role, ownership, staff permissions, device policy, and financial rules. Admin endpoints and server-to-server collections/payouts are not exposed by the gateway.

Sign-in uses the same email OTP flow as the mobile app. Cognito tokens and verified device sessions use tab-scoped session storage. Browser verification follows the existing register → challenge → RSA-SHA256 verify flow. Account-scoped non-exportable private keys and stable device IDs live in IndexedDB; atomic first creation prevents simultaneous tabs from overwriting the identity. The existing database format is preserved. Public keys and signatures use the existing backend format. Expired or missing temporary proof renews through challenge/signature verification of the persisted identity before owner requests, without registering a replacement or requesting another approval for a trusted browser. Concurrent renewals coalesce, and Web Locks serialize challenge/verify sequences across same-origin tabs when supported. Proof is bound to the signed-in account; logout/account changes discard ephemeral proof and late verification responses. A server-expired proof can resume a safe GET once, while writes are never automatically replayed. Pending browsers show approval instructions and an explicit approval check. Device errors route to verification, separately from login expiration, without retrying financial submissions. Private-browsing policies must permit IndexedDB/Web Crypto. Device identities are separated by browser profile and origin (scheme, host and port), so different localhost ports or production domains require separate approval. Clearing browser storage requires registering the browser again. Device recovery and replacement management remain in the mobile app/support flow.

## Implemented flows

- **Overview:** the premium welcome banner and connected-platform illustration, familiar toolkit cards, recent activity and owner summaries.
  The four Business Tools remain on Overview, with protected owner summaries below them. Counts come from paginated endpoint totals; amounts retain their currencies.
- **Online Stores:** paginated discovery; Name → Description → Summary creation without another payment; owner/staff workspace with Products, Sales, Customers, Reports, Team and Settings tabs. Full branding/contact/media/visibility settings, publish and confirmed deletion; physical/digital/service products with inventory, fulfillment, media, channels and marketplace review; customer CRUD/related sales, report periods/currencies, and owner-managed staff permissions.
- **POS:** paginated eligible-store selection, server product search, barcode/manual or supported camera input, cart/customer management, backend quotation/review, Fondeka payment collection, and cash Paid/Partially paid/On credit with due dates. Backend amounts/currencies remain authoritative. Receipts support share, print and download. Order creation has no automatic retry: an uncertain submission requires checking sales/support because the backend has no idempotent order-creation contract.
- **Payment links:** paginated Quick Charge, Invoice and Donation requests; complete create/edit configuration, public link/share/QR download/print, collection/history/payer details, linked transaction, and confirmed cancel/delete under backend eligibility rules. Local list filters are labelled as applying to the current page. Direct collection uses the shared method/wallet/phone/network selector, backend quote and account-scoped retry intent.
- **API:** expandable parent navigation with Wallets, Transactions and API guides pages. API credentials remain on the API landing page, with automatic default Business selection and collapsed, display-only operational/KYB details; API key metadata including revoked keys, self-service generation with one-time secret display and confirmed revocation; server-filtered, paginated API history; transaction details and manual status refresh; sanitized asynchronous crypto instructions. Business changes remount the view and discard stale requests. Missing Business/key/history responses have distinct empty states; failed/older backend routes show errors rather than empty success.
- **Settings:** the account’s first Business profile, with its ID, name/legal name, country, registration number and backend status/verification. Generated reference placeholders are hidden as names. An explicit Edit action reloads the owned Business, then saves only changed name, legal name, country and registration fields through customer-authenticated PATCH. Optional blanks clear with null. Status/KYB remain read-only, errors retain edits, and conflicts require reviewing current server values before retry. Successful resources immediately replace matching account-scoped list/detail cache values. Isolated demo reset remains available in a separate disclosure.

English/French owner terminology, forms, statuses and payment states ship together through the header language selector and explicit `Accept-Language`. Tool tabs, selected objects, filters and pagination use known internal URLs. The bounded account/language-scoped memory cache keeps loaded data after it becomes stale, refreshing it in the background on return or focus. Concurrent views share GETs; mutation invalidation and logout/account changes abort obsolete reads and reject late responses. Business Tools access loads once per authenticated workspace. Resume checks coalesce and revalidate a known grant at most once per minute without hiding loaded owner screens; temporary read failures retain the verified grant, while confirmed revocation and protected-operation denials lock it immediately. Initial checks, explicit access refresh and denied-operation recovery remain blocking. Session bootstrap runs once on portal entry/authentication changes rather than each route; normal API authentication and device-policy errors remain enforced. New pages still load their data initially; returning to loaded pages keeps useful content visible.

The [capability matrix](docs/business-tools-capability-matrix.md) records endpoint coverage, mobile references, browser adaptations and integration acceptance still required. Connected controls do not constitute production parity sign-off: real devices/permissions, signed uploads, external payments and trusted-device flows require authorized backend QA.

The API portal consumes `/customer-api/businesses/**`, never a merchant API key or admin token. Filters combine with AND, exact references preserve case, date bounds are inclusive local calendar days converted to Unix milliseconds, and pages are loaded on demand. Each amount retains its stored fiat currency. Crypto token amounts are shown separately. Business API payment views use the backend-normalized `PROCESSING`, `COMPLETED` and `FAILED` statuses. Unresolved provider/manual-review outcomes remain `PROCESSING`; cancellation/expiry appear as failure details, and refunds use the independent backend `refunded` flag. Business/KYB statuses do not introduce client-side payment gates. Owners can generate/revoke credentials using customer authentication; admins retain management access. Secrets appear once in component memory and are cleared on close or Business/navigation/logout changes, never persisted in browser storage, URLs or logs. Demo credential mutations are disabled. There is no reveal endpoint, payment submission control or webhook replay control in this portal.

API defaults to LIVE and provides a LIVE/SANDBOX selector in the shared header. The selected environment is held in account-scoped memory outside the owner-data gate, so access refresh/resume does not silently switch SANDBOX to LIVE; logout/account changes clear it. The selected environment is sent on credential issuance, key/history reads and reference-based details. Changing Business/environment remounts the scoped workspace, clears pagination and secret/detail dialogs, and aborts stale reads. Unexpected environments are rejected instead of showing live data as test activity. Credentials include environment labels and accept the corresponding `fdk_biz_` / `fdk_biz_test_` formats. Issuance refreshes only the scoped credential metadata so that refreshing the Business list does not immediately discard the one-time secret display.

Sandbox history uses `SBX` references and nullable financial transaction IDs. It has no links to generic numeric transaction details or inclusion in financial totals. Crypto fixtures are labeled not payable and have no copy-address, QR or invoice-opening controls. The environment-specific integration guide documents server-side scenarios and webhook environment verification; the browser never sends API-key-authenticated collections or payouts. Demo mode provides isolated fictional histories and keys for both environments, while credential mutations remain disabled. Backend sandbox support, the additive migration and compatible web/worker processes must be deployed before real sandbox credentials are issued; this portal does not deploy them.

The API wallet panel reads `/customer-api/businesses/{id}/api-wallets` with the selected environment and optional fiat currency. LIVE balances are explicitly account-wide and read-only. SANDBOX provides test funding and on-demand, paginated `/sandbox-wallets/{currency}/entries` history, shared across the account's Businesses in that currency. Movement amounts retain their sign; `balanceAfter` is an immutable snapshot, and payment links use the initiating Business's `SBX` reference. Currency checks do not create/fund wallets. Balances/history refresh after funding, observed terminal payment results and browser resume. No sandbox amount enters real reporting or Business Tools payment selection.

Test funding posts only to the authenticated customer `/sandbox-wallets/top-ups` route, with a stable `Idempotency-Key` header. The narrow proxy forwards that header only for test funding and sandbox conversion execution. Before sending, the original Business/currency/amount/key are saved in account-scoped session storage; double submission is blocked, and uncertain results, conflicts and rate limits retain the intent for an explicit identical retry, including after reload. Logout/account changes clear recovery. Replays show the returned movement snapshot and separately reload current balances. The demo simulates this locally, starts virtual wallets at zero, and preserves its earlier status-only transactions without retroactive money effects. New backend simulations use snapshotted virtual fees, gross payout debits, net collection credits and policy-dependent virtual refunds; the portal displays backend amounts and `refunded`, without calculating those effects. Deploy `20261110_business_api_sandbox_wallets.sql` and compatible web/worker binaries before enabling real wallet-backed sandbox usage; no backend migration or deployment is performed here.

SANDBOX also provides conversion preview and explicit confirmation through customer JWT/device-authenticated `POST /sandbox-wallets/convert/quote` and `POST /sandbox-wallets/convert`, under the selected Business. The server supplies all rates, fees, target amounts and balance snapshots; the portal never calculates a real conversion or hard-codes eligible pairs. Preview does not mutate wallets or create an intent, and editing any selection invalidates its quote. Execution may use updated fixtures, so the returned completed amounts are authoritative. Confirmation saves a separate account-scoped conversion key/body before sending, blocks double submission, and preserves the same intent across timeouts/reloads or Business changes. It never polls a financial transaction ID. Completion reloads current balances and invalidates ledger reads for both currencies; immutable snapshot balances remain labeled as such. Ledger `CONVERSION_DEBIT` and `CONVERSION_CREDIT` show a common `conversionId` without a payment link. The demo uses explicitly synthetic fixtures and local virtual balances only. Apply `20261111_business_api_sandbox_conversions.sql` after the wallet migration and deploy compatible backend binaries before using the real customer conversion routes; the portal performs no migration or rollout.

No aggregate API analytics endpoint exists, so this app does not download all transaction pages to manufacture totals. Existing stores are discovered independently from Business profiles; the UI does not invent a relationship absent from the commerce contract.

Payment guide request cards include **Available methods** and, for crypto, **Available networks**, with matching actions beside the payload-field explanations. Both open a read-only catalog browser using the customer-authenticated `GET /customer-api/businesses/{businessId}/api-catalog` route. It loads configured names without requiring an API key and keeps each guide specific to mobile money or crypto and collection or payout. All countries are included; only active payment methods and active associated crypto networks are shown in both LIVE and SANDBOX. LIVE additionally applies collection/payout and invoice-creation flags; active entries keep sandbox simulation rules. The active configured example method is selected on opening when available, exposing compatible networks as selectable cards in backend priority order. Copy controls return the exact `paymentMethodName` and `networkName`; method currency metadata never changes the request’s fiat wallet currency. The catalog refreshes on opening/return and supports manual refresh. Selection is ephemeral and account/Business/environment scoped. The existing authenticated proxy preserves device proof, locale and no-store; the backend must include the catalog addition. Empty or failed responses never fall back to a fixed method list. Published examples remain unchanged and this browser sends no merchant payments.

## Business Tools activation

The portal includes one account-level access guard and payment dialog for Payment links, Online Stores, POS and API management. Set `NEXT_PUBLIC_BUSINESS_TOOLS_ENABLED=true` only after the backend contract is deployed, pricing is approved and grandfathering is ready. It defaults to `false` to avoid activating a client paywall during rollout. This setting never changes backend enforcement. A protected endpoint's explicit `BUSINESS_TOOLS_ACCESS_REQUIRED` denial triggers access recovery regardless of the setting; an access lookup error or older backend's `404` shows retry rather than granting access or demanding payment.

When enabled, owner routes and overview widgets wait for `/customer-api/business-tools/access` before mounting their data queries. All four shortcuts remain visible. Access is based on `accessGranted`, including admin/migration grants without purchases. Login, device approval, settings and logout remain outside the gate. Public browsing, checkout and payer experiences are not gated by this owner-area integration.

Selecting a tool checks access on the current screen, then opens a compact desktop dialog or mobile bottom sheet when activation is needed. The background remains visible and inert; direct owner links show a static locked preview without starting protected requests. The English/French interface prioritizes the backend activation amount, billing badge, a short explanation, returned payment methods, fees and final total, with an Activate/Activer confirmation. Method lists scroll independently, and the summary and confirmation stay within reach. Once access is granted, the dialog closes and continues automatically to the known internal destination. Closing it returns to the usable workspace without cancelling a pending payment.

The shared purchase flow displays the Business Tools price and amount due from backend `pricing`, followed by payment processing fees and the final gross quote in normal currency units. Qualifying previous positive, completed, non-refunded store payments grant lifetime access through backend recognition, regardless of today's price or currency; the portal never calculates a top-up, infers eligibility from store history or demands a new payment record for an existing grant. Historical credit is shown only on accepted purchase snapshots. An obsolete partial-credit offer refreshes once for backend recognition, then shows review/support if access remains false, without a new purchase. Discovery supports returned balance wallets, mobile money, crypto networks and bank methods, using the versioned `X-Client-Version: 1.0.97` response and selected language. Payments use `BUSINESS_TOOLS_ACCESS` with exclusive fees. A disabled seeded offer shows unavailable activation with Back and Refresh actions and starts no payment discovery or quote. Zero due on an enabled, configured offer also refreshes once, then shows review/support if access is still false; it never grants access or submits a zero payment. Missing or malformed pricing is an error rather than a guessed charge. A pending purchase retains its accepted pricing snapshot and transaction instructions, even if today's offer has changed. A completed historical purchase with `BUSINESS_TOOLS_LEGACY_CREDIT_UNAVAILABLE` shows payment received/access review and cannot start another charge.

Before submission, the original payment selection and idempotency key are saved in account-scoped session storage. Uncertain results first check access and pending purchases; only an explicit continuation retries the identical intent. Accepted external purchases poll the purchase UUID sequentially, pause in the background and stop automatic checks after three minutes with a manual status option. Payment instructions use the returned transaction ID; asynchronous crypto invoices refresh without another purchase. Payment status alone never unlocks tools. Logout/account changes clear recovery and query state, and a denied owner write is never automatically replayed.

The demo returns a fictional existing access grant, so it remains navigable with the rollout setting enabled. No demo activation submits a real payment.

If an account already has access while an earlier purchase is still pending, tools open immediately. A separate payment-status notice provides a read-only status/instructions dialog and a support reference without starting another purchase or cancelling the existing one.

Payment selection uses the same country header detection and searchable country/calling-code catalog as the public checkout projects. A detected country takes priority; without hosting geo headers, the account country is used, then CD. A manual change stays selected during the current payment flow. Method discovery waits for a country, and changing country clears the previous method and quote. The shared selector groups Fondeka wallets, Mobile money, Cryptos and Bank in a grid accordion; wallets open first, with USD before other currencies and balances descending.

An unpaid bank-transfer activation advertises `canChangePaymentMethod` from the backend. Reopening the modal starts at payment-method selection; Back from the instructions returns there. The previous instructions remain available. Confirming another method sends a new idempotent intent with `replacePurchaseId`; the backend replaces the unpaid bank attempt atomically. Closing the modal starts no cancellation or charge. Customers who have already sent the transfer should keep the existing payment. Deploy the matching backend contract before enabling this flow; other in-flight payment methods retain their original recovery behavior.

Payment groups use distinct tinted headers, raised icons and framed rotating chevrons. Wallet tiles reuse the currency flags; crypto and mobile-money tiles use backend `logoUrl` values, with local fallbacks for missing or broken images. During Business Tools activation only, positive enabled wallets are checked against a backend exclusive-fee quote in their own currency before they become selectable. At most three read-only quotes run concurrently; only wallets covering the final total are shown. Pending checks, insufficient funds and unavailable checks have localized status/retry states. Changes to the account, country, pricing or balance cancel obsolete checks. The selected method still receives a fresh final quote for review before confirmation. This filtering does not change POS or payment-request collection eligibility.

## Guided Business tasks

Business creation uses one shared app-style flow: a focused card, progress, step-local validation, Back/Next and a final review. Store creation follows Name → Description → Review; product and payment-request steps branch by type. Customer, staff and API credential dialogs use the same shell. POS reveals customer and payment choices after cart construction. English and French share the same structure.

POS selection resolves stores before navigation. After access is granted, Overview preloads the first store page into a memory-only account/language cache; a quick POS click shares the same read. The backend total selects a direct `/stores/{id}/pos` route for one store, a focused chooser for multiple stores, or a create-store empty state for none. Failed reads offer Retry without guessing a count. Creating a store from POS retains the intent and offers Open POS with the returned ID. Store changes invalidate this cache, browser Back reuses loaded pages, and logout/account switch disposes it. Access remains cached across tool navigation; explicit recovery/resume checks still honor backend revocation.

Safe store/product/request draft fields survive a refresh within the current account session for up to 24 hours. Contact details, payment selections, private fulfillment values and secrets stay in memory. Logout/account switch clears drafts. Activation remains the shared contextual payment modal. See the [capability matrix](docs/business-tools-capability-matrix.md) for coverage and backend integration checks.

The shared response boundary normalizes Spring Data `VIA_DTO` pages (`content` with nested `page` metadata) to the portal’s list shape before caching. Older flat pages and array responses remain compatible. POS store resolution uses the backend total in either page format rather than treating a valid nested response as a load failure.

## Training file uploads and media-bucket CORS

Training uploads request `/customer-api/commerce/products/{productId}/training/assets/presign` through the authenticated customer client, then send the raw `File` directly to the original S3 URL using a separate XHR transport. The signed method and headers, including the exact signed Content-Type, are preserved. The direct request excludes credentials and portal/device headers, supports progress/cancellation, and never stores or logs the signed URL. Each retry requests a fresh capability. The curriculum stores only the returned private key and file name.

The browser needs a media-bucket CORS rule in addition to the backend signer’s existing S3 permissions. Reviewed exact-origin configurations are in [development CORS](deployment/s3-media-cors.dev.json) and [production CORS](deployment/s3-media-cors.production.json). Development includes the portal’s default port 4200 and the local 4300/4301 instances; production allows only `https://web.fondeka.com`. Confirm the actual bucket and deployment origins before applying either file. Read the existing CORS configuration first: `put-bucket-cors` replaces it, so merge existing rules rather than dropping them. Add staging origins explicitly when applicable. Do not add OPTIONS to AllowedMethods or wildcard production origins.

An OPTIONS 403 with `CORSResponse: CORS is not enabled for this bucket` blocks upload before PUT. After configuration, verify that a preflight with the exact portal Origin, requested method PUT, and requested headers content-type succeeds. A PUT 403 after a successful preflight requires its S3 code: SignatureDoesNotMatch indicates signing inputs differ; AccessDenied indicates a permissions/policy rejection; ExpiredToken/RequestExpired require a fresh capability and possibly renewed backend signer credentials. The UI shows safe status/code/request-ID details when the browser exposes them. Network/CORS failures without readable HTTP details remain distinct. Full S3 XML is discarded because it can contain signing inputs.

CORS does not grant object permissions and does not replace the prefix-scoped private-read policy for `commerce-training-assets/*`. Keep that prefix private in S3/CDN, verify anonymous reads fail and authorized short-lived reads work, and preserve public store/product media. No training files are uploaded by automated tests.
