## Platform adaptations and limits

- Camera barcode detection requires a secure browser context and `BarcodeDetector`. Browsers without support get manual code/SKU entry and keyboard-scanner support. Camera access is requested only after selecting Use camera. Microphone and location remain disabled.
- Web Share uses the browser’s native share UI when available and copies otherwise. Printing uses an isolated receipt/QR document. Receipts can be downloaded as HTML; browser print supports saving a PDF. A native OS PDF share sheet is not assumed.
- Images/video/digital files use the existing signed storage PUT flow, backend byte limits, supported types, video duration validation, progress and cancellation. Real storage CORS/configuration and authorized uploads require backend integration QA. Demo upload controls explain that a connected account is required.
- Store/sales/customer/staff lists are paginated. Filters explicitly labelled “this page” are local because those list endpoints do not expose server-side filtering. POS search uses its real search endpoint.
- A POS order-creation timeout is uncertain and is never automatically replayed. Check the owner sales list/support before creating another order; the backend has no idempotent POS-order creation contract. Existing order-payment retries retain the same order and payment key. Order access tokens stay in memory and do not enter bookmarked URLs or browser persistence.
- Backend-only/admin operations, unsupported product deletion, automatic recurring billing and webhook replay are not presented as working customer controls.

## Acceptance work

Automated checks cover exact proxy methods, account/cache isolation, store permissions, full-settings publishing, cash payment validation, supported currency discovery, safe receipt rendering, request collection idempotency and the existing access/purchase/credential/sandbox suites. Local browser QA covers representative English/French desktop and narrow layouts and demo owner workflows. Live wallet/provider payments, storage upload/cancellation, real staff accounts, backend enforcement and trusted-device approval must be checked on an authorized integration deployment before declaring cross-platform production acceptance.

For subsequent feature changes, update this table with the affected mobile/web/backend surfaces, shared terminology, endpoint/state/permission changes, desktop/responsive acceptance evidence and any explicit platform exception. Do not equate implementation with production parity sign-off.

Overview retains the premium presentation and four Business Tools. The redundant Business navigation item is removed; older /business links remain compatible. Overview stays navigable before activation, while protected summaries wait for access. Payment-request discovery and fee quotes include the request ID/code. POS collection excludes balance as in the mobile flow; account activation retains wallet payment. Public browsing/checkout links continue to the existing public commerce experience outside the owner gate. No public review or checkout endpoint is exposed through a wildcard proxy.

## Guided-flow acceptance

All creation flows share the same narrow card, step count/progress, local validation, review/Edit links, Back/Next placement, final submission lock and English/French structure. Desktop keeps the portal shell; narrow browsers keep the mobile hierarchy. Customer/staff/API subflows use a centered dialog or responsive sheet. Activation remains the existing contextual payment dialog.

Known internal URLs retain a validated `flow`/`step` and object selection. Browser Back/Forward preserves mounted values; required earlier decisions are revalidated before advancing or submitting. Non-sensitive store/product/request fields recover from an account-scoped, size-bounded session draft for up to 24 hours. Customer contact details, staff identities, settlement selections, fulfillment credentials, API secrets and uncertain payment submissions are not saved as form drafts. Drafts clear on cancellation, successful creation and logout/account switch. Invoice line-item editing and private fulfillment values remain in memory.

Automated checks cover step access/branch changes, final revalidation, safe draft recovery, malformed/expired storage and internal destination sanitization. Local browser checks cover store creation and success, Quick Charge creation and returned details, invoice line totals, the seven-step digital product branch and returned product, staff identity/permissions/review, unsaved navigation confirmation, 390px responsive cards, French structure and POS inline customer → quote → cash confirmation → receipt. Credential mutations remain disabled in demo; actual credential creation, real uploads and provider flows still require an authorized backend integration environment.

Payment selector update (web): follows fondeka-pay/fondeka-commerce country header detection and searchable country list. Vercel/Cloudflare/custom/CloudFront country headers select the initial filter, with account country then CD as fallbacks. The first method query waits for that selection. Manual changes take priority until the flow is closed and discard the previous method/network/phone/quote. Wallets are initially expanded; opening another type collapses the previous group and clears its method selection. Only backend-returned methods are shown. Automated checks cover mobile registration routing, country precedence and filters, catalog normalization and wallet/group ordering; local desktop QA confirms QR generation and the accordion/grid interactions. Hosting geo headers and real country-specific provider availability require deployment integration verification.

Account access caching (web): the authenticated workspace primes one in-memory Business Tools access result. Menu navigation, browser Back/Forward and owner deep links reuse that account-level result without a request or activation-dialog flash. Initial/required refreshes still block owner queries. Resume/focus, locale changes, explicit refresh, payment completion and `BUSINESS_TOOLS_ACCESS_REQUIRED` bypass the cache; logout/account switch/page reload create a fresh scope. An active account’s resource-specific denial blocks that resource without turning other tools into payment prompts. Automated checks cover single-read navigation, concurrent initial entry, forced refresh/expiry, pending recovery, failed-read retry and new-account isolation.

POS routing update (web): the shared activation continuation now resolves the intended POS store decision before routing. English/French chooser, empty and retry states use the same store contracts and permissions; no mobile or backend contract change is needed. Automated coverage verifies total-based routing, in-flight coalescing, cached Back navigation, access denial/grant, invalidation on store changes, stale account results, pagination/permissions and known internal destinations. Production build includes the canonical `/stores/[id]/pos` route. Live account and responsive visual verification remain separate from these automated checks.

API documentation update (web): API & developers now reads the published merchant guide bundle on demand, with OpenAPI v1/Postman downloads and preserved relative source-example links. Portal navigation and recovery messages ship in English/French; the upstream technical guides and code remain the explicitly labelled English publication. A full French translation of the published technical guides is not included in the upstream release. No mobile, backend, runtime documentation, payment submission or authentication contract changes are included. Artifact hashes, public-only file selection, sandbox Postman guards and link/destination handling have automated coverage.

Local documentation verification: the isolated demo showed the published quickstart, working Webhooks navigation and browser Back restoration. At 390px, the topic list becomes a French-labelled native picker and the selected guide remains readable within the mobile shell. Public OpenAPI/Postman/guide/example responses returned 200 and matched their release hashes on the real local server. No credentials were issued and no payment examples were executed.
